# 設計書：タロショット Web 化（GAS）

**目的**: マスター Google スライドは説明・入口リンク用に公開し、本体は **Web アプリ**として提供する。利用者は **自分の Gemini API Key** と **自分の Google ドライブ**だけで使えるようにする（オーナーのキー／Drive を共有しない）。

**現状**: コンテナバインド（スライドメニュー → モーダル `TaroshotDialog`）。設定は `Script Properties`。画像用・スライド用フォルダ ID は手入力。任意で `doGet` → `Upload.html` の Web アプリあり。

**方針**: 小さなステップで進め、**各ステップ後にライブテスト**してから次へ進む。既存の `Gemini.gs` / `SlidesHelper.gs` / `DriveHelper.gs` の生成ロジックは可能な限り流用する。

**関連**: `README.md` / `src/README_GAS.md` / `設計方針_画像toJSON_GAS.md`

## 1. ゴール / 非ゴール

### ゴール

- [ ] 公開 URL を開けばタロショット本体が使える（スライドコピーや GAS 貼付が不要）
- [ ] 設定は利用者ごと（API Key・フォルダ ID が混ざらない）
- [ ] Drive のフォルダ ID 手入力を原則不要にする（自動作成＋更新可能）
- [ ] 生成されたスライド・画像は **利用者の Drive** に保存される
- [ ] Gemini 呼び出しは **利用者が入れた API Key** のみを使う

### 非ゴール（この設計の範囲外）

- [ ] Google Workspace Marketplace アドオン化（将来候補）
- [ ] サイドバー UI への移行（Web 化とは別物。必要なら別設計）
- [ ] マスター上の閲覧者向け GAS ボタンで `makeCopy`（閲覧のみでは不可。必要なら別ステップ）
- [ ] オーナー実行の Web アプリ（鍵・Drive がオーナー側になるため採用しない）

## 2. 目標アーキテクチャ

```text
[公開マスター スライド]  … 説明・注意・「タロショットを開く」リンクのみ（設定なし）
           |
           v
[Web アプリ URL]  … HtmlService（本体 UI）
           |
           +-- User Properties … GEMINI_API_KEY / IMAGE_FOLDER_ID / OUTPUT_FOLDER_ID
           |
           +-- 利用者の Drive … 画像フォルダ / 出力フォルダ / 新規スライド
           |
           +-- Gemini API     … 利用者の API Key
```

| 項目 | 採用 |
|------|------|
| GAS 形態 | **スタンドアロン**推奨（スライドに紐づけない）。当面は既存プロジェクトからデプロイでも可 |
| 入口 | `doGet` → 本体 HTML |
| 実行ユーザー | **ウェブアプリにアクセスしているユーザー** |
| アクセス | Google アカウント必須（全員 or 組織内） |
| 設定保存 | **`PropertiesService.getUserProperties()`** |
| Drive | 初回自動で 2 フォルダ作成。再作成・差し替え可能 |
| 手入力必須 | **Gemini API Key のみ**（理想 UX） |

## 3. 設定・フォルダ仕様

### 3.1 User Properties キー（現行キー名を踏襲）

| キー | 必須 | 説明 |
|------|------|------|
| `GEMINI_API_KEY` | ○ | 利用者の Gemini API Key |
| `IMAGE_FOLDER_ID` | ○（自動作成後） | 画像用フォルダ |
| `OUTPUT_FOLDER_ID` | ○（自動作成後） | スライド／一時 JSON 用フォルダ |
| `GEMINI_MODEL` | × | 任意。未設定時は `CONFIG.DEFAULT_GEMINI_MODEL` |

- API Key はログ・エラーに出さない（現行方針を維持）。
- UI 表示はマスク（現行 `maskApiKey`）。

### 3.2 自動作成するフォルダ（案）

マイドライブ直下（または固定ルール）:

```text
タロショット/
  ├── 画像/
  └── スライド/
```

| 操作 | 挙動 |
|------|------|
| 初回「Drive を準備」 | 上記が無ければ作成し、ID を User Properties に保存 |
| 「フォルダを再作成」 | 新しい `画像` / `スライド` を作り ID を上書き。旧フォルダは **残す**（誤削除防止）。必要なら後で手動削除 |
| 既存 ID が無効 | エラー表示のうえ、再作成を促す |

## 4. UI 仕様（Web 本体）

画面は 1 ページ（現行 `TaroshotDialog` をベースにページ向け調整）。

1. **API Key** … 入力＋登録（必須）
2. **Drive 状態** … 準備済みならフォルダ名 or 簡易表示。「準備する」「再作成」ボタン
3. **画像登録** … ローカル画像選択 → 画像フォルダへ（登録前クリアは現行踏襲）
4. **スライド生成** … Step1（Gemini）→ Step2（新規スライド）現行分割を維持可
5. **スライド表示** … 直近 URL を開く

レスポンシブは後回し可。まずデスクトップ幅でライブテストする。

## 8. リスクと回避

| リスク | 回避 |
|--------|------|
| デプロイを「自分」実行にしてしまう | Step 7 のチェックを必須化 |
| Script Properties に Key が残る | Step 3 / 9 で User Properties のみに |
| 画像フォルダのクリアが他人のフォルダを消す | User Properties の ID のみ操作。共有フォルダを設定させない |
| 再作成で旧データ迷子 | 旧フォルダは残す。UI に「旧フォルダは残ります」と表示 |
| 初回権限で離脱 | マスターに「許可が必要」と明記。権限リストを最小に |
| 大きな UI 改修とロジック改修を同時にやる | 本設計どおり Step を分け、毎回ライブテスト |
